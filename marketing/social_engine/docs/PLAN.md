# Social Engine Implementation Plan

**Sensitive:** yes, because the engine handles API tokens and secrets (`.env*`) and performs outward-facing publishing.

**Design source:** [`SPEC.md`](SPEC.md), with owner decisions D19 to D32 applied on 2026-11-04. Where this plan and the spec disagree, stop and ask.

**Goal:** a local Windows pipeline that researches, scripts, voices and renders a reel, and sends it to the owner on Telegram. Nothing is posted without a per-post tap. It ships in `engine.mode: test`, and the launch gate in spec Section 13 stays closed.

**How the work is ordered:** everything that can be built and tested without Azure, Telegram or a phone comes first (Part 1). Live steps that need the owner's credentials are separate (Part 2). No agent runs a Part 2 step without the owner's go-ahead.

```
A ─┬─► Group 1, parallel: B  C  D  E  F  G  H ─┬─► K ─► Part 2 live steps
   │                                           │
   └─► after B, Group 2, parallel: I  J ───────┘
L (copy report) runs last. It edits nothing outside its own report.
```

## 1. Ground rules for every batch

**Worktree.** One git worktree and branch per batch, one agent per batch (rule 06 section 2). Do not push, merge or deploy unless the orchestrator asks.

**Files.** A batch edits only the files in its row of the ownership table (Section 4). Needing another batch's file is a stop-and-ask. All code lives in `marketing/social_engine/`. `ai_service/`, `flutter_app/` and `web_app/` are read-only, and `ai_service/price_tracker.py` in particular is owned by another task.

**Plan checkboxes.** The orchestrator ticks `- [x]` here after each batch merges (rule 05 section 4). Batch agents do not edit this file or `SPEC.md`, so parallel batches never touch them.

**TDD (rule 05).** For each task: write the named test, run it and confirm it fails for the intended reason, write the minimal code, run it and confirm it passes, then run the batch gate. No stubs or placeholder handlers in engine code.

**Hermetic tests.** Mocks only. No test calls Telegram, Claude, Azure, any platform or Supabase, and no test posts anything. No test reads a real `.env` or the real `data_root`. Tests use `tmp_path` as `data_root`. `claude`, `adb` and `npm` are faked at the subprocess boundary. The Azure SDK sits behind a seam, and tests never construct it.

**Stop and ask the owner, through the orchestrator (rule 06 section 7):** any account, real key, spend, real post, data deletion, machine-wide install, Task Scheduler registration, or blocking note. Agents never read `.env` and never ask for a key in chat.

**Review.** Each batch gets Round 1 and Round 2 (Opus 5.5, effort high) and Round 3 (Fable, effort high), by fresh subagents, because the plan is sensitive. Sensitivity is never lowered for a batch.

**Commits.** Conventional commits per task, such as `feat(social-engine): ...` and `test(social-engine): ...`.

Notes for implementers:

- **Network ban.** Do not use `pytest-socket --disable-socket`. Windows `asyncio` needs a local socket pair for its event loop, and blocking socket creation would break the bot's tests. Task A1 builds a small fixture that blocks DNS and any connection except loopback.
- **Log redaction.** `python-telegram-bot` logs through `httpx` and `anthropic` 2.x uses `httpx2`. Both loggers are set to `WARNING`.
- **Anthropic SDK.** Load the `claude-api` skill before Task D2, and check SDK usage against it and the SDK's changelog, because 2.4.0 is newer than that skill's upgrade guide.


**Remotion gate (batch F, and K's end-to-end check).** `npm` never runs inside the repo (spec Section 4), so sync first:

```powershell
& $py -m core.remotion_sync --data-root "$env:LOCALAPPDATA\SocialEngine"
```

The first `npm install` happens in `remotion_work\`. `core.remotion_sync --pull-lock` then copies `package-lock.json` back to the repo. The first render downloads Remotion's headless browser, which is a free tool download, once, and is not a test dependency of the Python suite.

**App gates.** Rule 06 section 6 applies as written to every batch, unless the owner waives it: `flutter analyze`, `flutter test` and `ai_service` pytest run before each review round and before committing. Batches still must not change `flutter_app/` or `ai_service/`. If a batch needs to, it is out of scope: stop and ask.

### 2.4 FFmpeg: no install by default

Remotion [ships FFmpeg](https://www.remotion.dev/docs/cli/ffmpeg) through `npx remotion ffmpeg`, limited to H.264, H.265, VP8, VP9 and ProRes. The plan does not depend on a separate install:

- Bitrate retries are re-renders through Remotion, not FFmpeg re-encodes.
- The conform and size checks use a pure-Python MP4 box reader (Task G2), so tests need no FFmpeg, and no `ffprobe` either, which the docs page only links to.
- Trimming, remuxing and metadata stripping use `npx remotion ffmpeg` from `remotion_work\`. Task F7 proves each operation on this laptop.

**Owner gate LIVE-0, only if F7 fails:** ask the owner to approve `winget install Gyan.FFmpeg`, then set `render.ffmpeg_path`. Do not install it without that approval.
